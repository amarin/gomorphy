# Почему парадигмы с одинаковыми «окончаниями» на одинаковых позициях не склеиваются (сравнительная степень)

**Дата:** 2026-09-15 (дополнено в тот же день, отдельная сессия)
**Статус:** обе исходные гипотезы пользователя по существу
**опровергнуты**; найдена реальная причина (корень хранится внутри
суффикса) и попутно подтверждён отдельный **баг** (побайтовый LCP-срез
режет внутри руны → 61.7% суффиксов shard 0 невалидны как UTF-8).
Дополнение 1: третья гипотеза (перенос константного тега в корень)
**подтверждена частично** (82.8%/93.2% случаев), эффект на размер мал
(4.3%/39.1% парадигм по шардам). Дополнение 2: механизм фикса
корня-в-суффиксе найден и проверен на реальных данных (формат уже
содержит нужную инфраструктуру, не используемую OpenCorpora-импортёром),
точный количественный эффект — не пересчитан по всем леммам, только
верхняя граница.
**Проверял(а):** Aleksey Marin (asmadews@gmail.com)
**Связанные документы:** [0002-paradigm-tagset-binary-encoding.md](0002-paradigm-tagset-binary-encoding.md), [2026-09-14-suffix-sharding-design.md](../superpowers/specs/2026-09-14-suffix-sharding-design.md), [stage-17-optimize.md](../implementation/stage-17-optimize.md)

## Контекст

Скомпилированный словарь `.data/opencorpora/opencorpora.dat` (2 шарда)
содержит секцию суффиксов `suffixes-0`/`suffixes-1`:
массив `[]string`, каждой парадигме соответствуют `suffix_id[]`
и `tag_id[]` (см. `pkg/morphology/internal/format.go`,
`EncodeParadigms`, `DecodeParadigms`).

Пользователь, просматривая секцию суффиксов, увидел **большие группы
парадигм с одинаковыми окончаниями на одинаковых позициях**, например:

```
ёмкостнее / ёмкостней / поёмкостнее / поёмкостней
абажурнее   / абажурней   / поабажурнее   / поабажурней
бордажнее   / бордажней   / по-...        / ...
боригеннее  / боригенней  / по-...        / ...
```

(парадигма сравнительной степени: `COMP,Qual`, `COMP,Qual,V-ej`,
`COMP,Qual,Cmp2`, `COMP,Qual,Cmp2,V-ej` — 4 формы). Наблюдение:
«хвосты» у всех групп одинаковые (`-нее / -ней / по-нее / по-ней`),
а парадигм много — почему они не сливаются в одну?

Импортно-дедупликационный путь (`pkg/morphology/importers/opencorpora/import.go`):

1. Для каждой леммы `stem := lcp(lem.forms)` (`import.go:136`) —
   **побайтовый** LCP (`lcp`, `import.go:350`, сравнивает `[]byte`).
2. Для каждой словоформы `suffix = frm.text[len(stem):]`
   (`import.go:143-146`) — **остаток после LCP-префикса**, а не
   «окончание» в морфологическом смысле.
3. Парадигма `(suffix_id[], tag_id[])` дедуплицируется ключом
   `paradigmKeyHash(suffixIDs, tagIDs)` (`import.go:184-195`), без
   префиксов (`import.go:251` — для OpenCorpora префикс всегда `"-"`).

Вывод 1+2+3: склейка возможна **только** при одинаковом полном списке
суффикс-ID и одинаковом списке тэг-ID. ID однозначно отражают
**строки** суффиксов (таблица `suffixes-N`), не «окончания».

## Гипотеза (пользователь)

1. **H1 — баг склейки:** компилятор теряет/плющит тождественные
   парадигмы; «раздельные хвосты одинаковых парадигм» — признак
   битой дедупликации.
2. **H2 — тэги различаются:** группы не сливаются, потому что у них
   отличаются морфологические теги (например, одушевлённость), а ключ
   хэширует и суффиксы, и теги.

## Эксперимент

**Данные:** реально собранный `.data/opencorpora/opencorpora.dat`
(сборка — `./deploy/gomorphy_build compile`), все секции прочитаны
существующими функциями пакета (`OpenContainer`, `DecodeStrings`,
`DecodeTagSet`, `DecodeParadigms`).

**Инструменты:** временный `_test.go` в `pkg/morphology/internal`
(`zz_research_paradigm*.test.go`, файлы не сохранены в репозитории),
вызывающий только экспортируемые функции пакета + хелпер
`utf8Valid` (`unicode/utf8.ValidString`).

**Метод:**

- Прямая проверка целостности дедупликации (H1): построить
  `(суффикс-строки → парадигма)` и `(тэг-последовательность → парадигма)`,
  подсчитать конфликты «одна пара ключей → разные id».
- Прямая проверка H2: найти суффикс-сигнатуры, разделённые на 2+
  тэг-последовательностей (сколько и какие).
- Побайтовая репродукция `lcp()` для конкретных лемм из `dict.xml`
  (для «ёмкостнее»/«абажурнее»/«бордажнее»/«боригеннее»/«яснее»)
  в Python и сверка с реальными строками секции суффиксов: вычисление
  `stem=lcp(forms)` и `suffix=form[len(stem):]`, проверка `utf8.Valid` на
  результате.

тэгов)` соответствует ровно одному id парадигмы:

|---|---|---|---|

Тех «плюснутых/потерянных» парадигм, которые должен был бы дать баг

канонических пар. Ни одной повторяющейся «хвостовой» парадигмы не найдено.

### H2 справедлива в общем виде, но НЕ для сравнительных групп

`TestResearchH2TagDiff` / `TestResearchSameSuffixDiffTags`:

| Shard | Суффикс-сигнатур | Разбитых разными тэгами |
|---|---|---|
| 0 | 16 875 | 551 |
| 1 | 249 | 74 |

Примеры реальных «одинаковые суффиксы — разные теги» (shard 0):

- paradigm 40: суффиксы `[ый ого ому ого ий им ом ая ой ой ую...]`,
  тэги `ADJF,Qual,…` против `ADJF,…` (качественное vs прочее
  прилагательное);
- paradigm 44: `ADJF,…` против `ADJF,Geox,…`;
- paradigm 45: `NOUN,anim,masc,Name,…` против `NOUN,anim,masc,…`;
- paradigm 30: `NOUN,inan,masc,Geox,…` против `NOUN,inan,masc,…`.

Это **корректное** отсутствие склейки: одинаковая поверхностная схема
при разных тэгах. Но к группам сравнительной степени это **не
относится**: их тэг-последовательности **попарно идентичны**.

### Реальная причина: суффикс = словоформы минус LCP-префикс, корень внутри суффикса

В `dict.xml` сравнительная степень — **отдельная 4-форменная лемма**
(не часть леммы исходного прилагательного):

```
LEMMA ёмкостнее  | forms: [ёмкостнее, ёмкостней, поёмкостнее, поёмкостней]
LEMMA яснее      | forms: [яснее, ясней, пояснее, поясней]
LEMMA ёмкостный  | forms: [ёмкостный, ёмкостного, ...]  (27 форм)  — своя лемма
LEMMA ёмкостен   | forms: [ёмкостен, ёмкостна, ёмкостно, ёмкостны] — краткая
```

Для такой леммы LCP всех 4 форм пуст (форма на «по-» расходится с
основной на первом символе), поэтому **каждая словоформа целиком
становится суффиксом**:

```
ёмкостнее  → suffix "ёмкостнее"
ёмкостней  → suffix "ёмкостней"
поёмкостнее→ suffix "поёмкостнее"
...
```

«Окончание» (`-ее / -ей`) действительно одинаковое на одинаковых
позициях — но в **конце каждой из разных строк суффикса, начинающейся
с корня слова**. Разные корни (ёмкостн-, абажурн-, бордажн-,
боригенн-) → разные строки суффиксов → разные `suffix_id` → разный
ключ дедупликации. Тэги при этом общие — поэтому получается **одна
многочисленная группа парадигм с идентичным тэг-списком и разными
суффиксами**, ровно та, что видит пользователь:

| Тэг-последовательность | Парадигм в shard 0 | Парадигм в shard 1 |
|---|---|---|
| `COMP,Qual / COMP,Qual,V-ej / COMP,Qual,Cmp2 / COMP,Qual,Cmp2,V-ej` | **7 597** | 19 |
| `COMP / COMP,V-ej / COMP,Cmp2 / COMP,Cmp2,V-ej` | **7 136** | 4 |

Это **не баг**: gomorphy не хранит «окончания», он хранит
«суффикс = остаток формы после общего префикса леммы». Группу
сравнительных можно было бы склеить только изменив модель (например,
хранить отдельно префикс «по-» и вычитать LCP-префикс на уровне
глагольных форм) — но с текущей моделью «суффикс = пост-LCP-остаток»
различные корни в суффиксах делают склейку невозможной по построению,
и это соответствует данным 1:1.

### Найденный попутно баг: побайтовый LCP режет внутри руны → 61.7% суффиксов невалидны как UTF-8

`lcp()` (`import.go:350`) сравнивает `[]byte`, а не руны. Для лемм, у
которых формы расходятся **внутри первого UTF-8-символа**, LCP
останавливается на границе байта внутри символа, и `frm.text[len(stem):]`
даёт строку, начинающуюся со «съеденного» байта.

- «ёмкостнее»: `ё = d1 91`, форма на «по-» = `п = d0 bf` — первые байты
  **разные** (`d1 ≠ d0`) → `LCP = ""` → суффиксы валидны, таблица чистая.
- «абажурнее»: `а = d0 b0`, форма на «по-» = `п = d0 bf` — первые байты
  **совпадают** (`d0 = d0`), второй байт разный (`b0 ≠ bf`) → `LCP = d0`
  (1 байт, середина руны) → `suffix = форма[1:]`, у суффикса съеден
  первый байт UTF-8 — строка **невалидна**.
- «бордажнее»/«боригеннее» — то же самое (б/п в блоке `d0`).
- Любое слово, начинающееся на букву из блока `d0` (а…п), у которого
  есть форма с префиксом «по-», получает корректно склеивающуюся по
  байтам, но невалидную как текст запись.

Подтверждение количествами (`TestResearchInvalidUtf8Count`,
`TestResearchInvalidUtf8Paradigms`):

| Shard | Суффиксов | Невалидных UTF-8 | Доля невалидных | Парадигм с ≥1 невалидным суффиксом |
|---|---|---|---|---|
| 0 | 65 534 | 40 442 | 61.7% | 10 385 из 17 934 (57.9%) |
| 1 | 688 | 179 | 26.0% | 53 из 529 |

Связь с большими группами (`TestResearchLargestTagGroups`):
в группе `COMP,Qual` (7 597) невалидных суффиксов в 4 760 парадигмах —
это ровно группы «абажурнее/бордажнее/боригеннее…» (буквы блока `d0`);
ранее посчитанные «2837 парадигм» из первого прогона — это **только
валидное подмножество** той же группы (7 597 − 4 760 = 2 837 — точно,
«2501» из первого прогона = 7 136 − 4 635).

Семантически такие суффиксы остаются корректными на байтовом уровне
для DAWG (ключ `stem+suffix` восстанавливает полную словоформу побайтово),
поэтому `lookup` не ломается, но **таблица суффиксов в `.dat` содержит
мусорные строки**, которые нельзя интерпретировать как текст: это видит
пользователь, и это ломает любой консьюмер, трактующий суффиксы как
UTF-8 (обрезка завершающих символов слова, нормализация и т.п.).

## Выводы

1. **H1 (баг склейки) — опровергнута.** Дедупликация парадигм 1:1
   (17 934 = 17 934 пар, конфликтов 0). Дубликатов «хвостов» нет;
   слияние происходит всегда, когда совпадают полные списки
   суффикс-ID и тэг-ID.
2. **H2 (теги) — верна в общем виде ('551'/'74' случаев), но не
   объясняет наблюдаемые группы сравнительной степени**: там
   тэг-последовательности идентичны, различаются только суффиксы.
3. **Настоящая причина не-склейки** — в модели хранения: «суффикс»
   в gomorphy это не окончание, а остаток словоформы после общего
   LCP-префикса. Для лемм сравнительной степени LCP пуст, поэтому
   **корень слова живёт внутри суффикса**, разные корни → разные
   суффиксы → разные парадигмы при общих тегах. Это поведение
   согласовано с данными и с `paradigmKeyHash`.
4. **Найден и подтверждён отдельный баг**: `lcp()` побайтовый,
   режет внутри руны для лемм, у которых формы расходятся в первом
   символе (любое слово на букву из блока `d0` + форма на «по-»).
   Эффект: 61.7% суффиксов shard 0 невалидны как UTF-8, затронуты
   57.9% парадигм. Функционально lookup не страдает (побайтовое
   восстановление `stem+suffix`), но таблица суффиксов содержит
   нечитаемые строки — необходимое следствие и для будущих
   потребителей суффиксов.
5. **Если склейка сравнительных нужна** — это изменение формата
   (модель пар «префикс + окончание» вместо «LCP + пост-LCP-остаток»
   для таких лемм / вынос «по-» в префикс), отдельная задача вне
   рамок данного исследования.
6. **Фикс бага из п.4** — заменить `lcp()` на руна-ориентированный
   (усекать результат до границы руны), либо, осознанно храня
   байтовые срезы, маркировать такие суффиксы; но текущее состояние
   (невалидные UTF-8 строки без какой-либо разметки) является дефектом
   данных в `.dat`.

## Дополнение 1 (2026-09-15, отдельная сессия): формальная проверка H2 — константность тег-дельты

**Статус:** гипотеза пользователя о «переносе константного тега в корень»
подтверждена частично: структура различий в H2-конфликтах в
большинстве случаев (не во всех) допускает такое разложение; эффект на
размер `.dat` при этом мал и полностью независим от находки про
корень-в-суффиксе (см. «Дополнение 2» ниже — именно там основной
рычаг).

### Контекст

Основной текст выше установил только факт: 551/74 суффикс-сигнатур
(shard 0/1) расщеплены 2+ различными тег-последовательностями (раздел
«H2 справедлива в общем виде...»). Не была проверена *структура*
различия: является ли оно константной добавкой/изъятием одной и той
же граммемы на **каждой** форме парадигмы (свойство леммы) — именно
это нужно для идеи «вынести граммему в корень, склеивать по мере
поиска в глубину».

Отдельно важный факт для реализации: `xmlHandler` в
`import.go` уже разделяет граммемы на `lemGrams` (из `<l>`, персистентны
на всю лемму) и `formOwnGrams` (из `<f>`, за форму) — см. поля структуры
(`import.go:278-281`) — но `OnFormEnd` (`import.go:336-347`) сразу же
плющит их в одну строку (`strings.Join(all, ",")`, строка 344) и
регистрирует как единый `TagSet`-ID. Разделение для хранения раздельно
от формы физически возможно без переработки сканера XML — оно уже
собрано, просто выбрасывается на этом шаге.

### Гипотеза (пользователь), H3

Если различие тегов в H2-конфликте устроено как одна и та же
добавленная/изъятая граммема на **каждом** индексе формы парадигмы (то
есть является свойством леммы, а не конкретной словоформы), то можно
хранить эту граммему один раз на лемму (например, привязав к корню/DAWG-
payload), а не дублировать её во всех вариантах парадигмы — и собирать
итоговый тег на лету при поиске (тег леммы ∪ тег формы), сократив число
различных парадигм.

### Эксперимент

Метод: для каждой суффикс-сигнатуры с 2+ различными тег-
последовательностями взять по представителю каждой уникальной
последовательности, попарно сравнить с базовым представителем —
разложить каждый тег на граммемы (`strings.Split(tag, ",")`), вычислить
symmetric difference (added/removed) множеств граммем на каждом индексе
формы, проверить, одинакова ли эта дельта для всех индексов. Отдельно —
верхняя граница экономии числа парадигм при слиянии всех H2-групп
(без учёта структуры дельты) и при слиянии только «константных» групп.

Инструменты: тот же метод, что в основном исследовании (временный
`_test.go` в `pkg/morphology/internal`, экспортируемые функции пакета:
`OpenContainer`, `DecodeTagSet`, `DecodeParadigms`), на реальном
`.data/opencorpora/opencorpora.dat`.

### Результаты

| Shard | H2-конфликтов | Константная дельта на всех формах | Не константная |
|---|---|---|---|
| 0 | 551 | 456 (82.8%) | 95 (17.2%) |
| 1 | 74 | 69 (93.2%) | 5 (7.2%) |

Примеры не-константных случаев (реальные, shard 0/1):
- единичная форма с точечной пометкой (`Infr`/`Slng`/`Abbr`), не
  затрагивающей остальные формы парадигмы — похоже на разметку
  OpenCorpora на уровне конкретной словоформы, а не леммы;
- один случай в shard 1, где суффиксы **случайно совпали** у двух
  генетически разных парадигм с разным порядком падежей
  (`Geox,femn,inan` против `Init,Name,anim,ms-f`) — это коллизия
  суффиксных строк между разными объектами, а не «одна парадигма +
  добавка тега».

Экономия числа парадигм при слиянии:

| Shard | Всего парадигм | Экономия (только константные группы) | Верхняя граница (слияние всех same-suffix групп без учёта тегов) |
|---|---|---|---|
| 0 | 17 934 | −770 (4.3%) | −1 059 (5.9%) |
| 1 | 529 | −207 (39.1%) | −280 (52.9%) |

### Выводы

1. **H3 подтверждена частично**: 82.8% (shard 0) / 93.2% (shard 1)
   H2-конфликтов имеют константную на уровне леммы дельту тега —
   годны для выноса в «тег леммы». Оставшиеся 17.2%/7.2% — нет
   (точечные пометки отдельных форм, редкие суффиксные коллизии между
   разными объектами) — реализация требует fallback-пути, а не
   универсального механизма без исключений.
2. **Эффект на размер мал и не «радикален»**: сокращение числа парадигм
   на 4.3% (shard 0) / 39.1% (shard 1); `paradigms-N` — и так лишь ~4%
   файла, так что в абсолютных байтах эффект — доли процента от
   `.dat` (shard 0) и незначим в абсолюте (shard 1, файл мал изначально).
3. **Эта ось полностью независима от корня-в-суффиксе** (см.
   «Дополнение 2»): там теги идентичны, дублирование идёт по суффиксам
   из-за пустого LCP, а не по тегам — эффект там на два порядка больше
   по числу парадигм (82% shard 0 против 4.3% здесь).
4. **Точка встраивания при реализации**: `OnFormEnd` (`import.go:341-345`)
   — не плющить `lemGrams`/`formOwnGrams` в одну строку, а хранить их
   раздельно. Предпосылка: атомарный `tagset` (уже описан как
   backlog-кандидат №3 в
   [research 0002](0002-paradigm-tagset-binary-encoding.md)) — иначе
   композиция «тег леммы ∪ тег формы» на лету всё равно требует
   материализации полной строки на каждый lookup, теряя выгоду.
5. **Рекомендация**: не приоритетно для Этапа 17 при текущих цифрах.
   Рассматривать отдельно от корня-в-суффиксе (Дополнение 2), если
   вообще браться — и то скорее как чистка модели, чем как рычаг
   сжатия.

## Дополнение 2 (2026-09-15, та же сессия): корень-в-суффиксе — что можно
сделать и какой эффект

См. отдельную выжимку, отправленную пользователю в этой же сессии —
кратко: формат уже содержит нужный механизм (`Paradigm.Prefix(form)`,
секция `prefixes`), используемый pymorphy2-импортёром
(`defaultPrefixes = []string{"", "по", "наи"}`,
`pkg/morphology/importers/pymorphy2/import.go:19`), но не используемый
OpenCorpora-импортёром (`import.go:193`: `prefixes := make([]uint16,
len(lem.forms))` — всегда индекс 0). Проверено на реальном
`dict.xml` (лемма `поправимее`, id 259490:
`forms=[поправимее, поправимей, попоправимее, попоправимей]`,
`Cmp2`-формы буквально равны `"по"+базовая форма`): если отделять «по»
по грамматической пометке `Cmp2` **до** вычисления LCP (а не после, и
не поверх уже посчитанного в `.dat` суффикса — ретрофит поверх старого
LCP даёт артефакты вроде корня `поп` вместо `по`+`поправим`, что видно
на этом же примере), парадигма схлопывается к канонической форме
`prefix=["","","по","по"], suffix=["е","й","е","й"]`, идентичной для
`поправимее`, `яснее` и любого другого прилагательного с этим паттерном
сравнительной степени — независимо от корня, потому что корень нигде
не хранится в парадигме, а восстанавливается из буквального текста
слова в `words.dawg` через `TrimPrefix`/`TrimSuffix`
(`pkg/morphology/parse.go:198-221`).

**Точный количественный эффект пересчитан на реальных данных** (Task 3
исследовательской SDD-сессии `2026-09-15-comparative-prefix-split`,
фикс реализован в `stripCmp2Prefix`, `import.go`): фикс собран
(`./deploy/gomorphy_build compile` на полном `.data/opencorpora/dict.xml`,
~400K лемм) и словарь пересчитан теми же экспортируемыми функциями
пакета, что и в оригинальном исследовании (`OpenContainer`,
`DecodeStrings`, `DecodeParadigms`, `DecodeTagSet`, временный `_test.go`
в `pkg/morphology/internal`, удалён после измерения).

| Метрика | До фикса | После фикса |
|---|---|---|
| Число шардов | 2 | **1** (после схлопывания всё уместилось в один shard — таблица суффиксов больше не подходит к границе `suffixShardLimit`=65536) |
| Всего парадигм, shard 0 | 17 934 | **3 245** |
| Всего парадигм, shard 1 | 529 | — (шард 1 больше не существует) |
| Суффиксов, shard 0 | 65 534 | **6 080** |
| Невалидных UTF-8 суффиксов, shard 0 | 40 442 (61.7%) | **0 (0.0%)** |
| Невалидных UTF-8 суффиксов, shard 1 | 179 (26.0%) | — |
| Байт таблицы суффиксов, shard 0 | ~1.38 МБ | **75 618 байт (~73.8 КБ)** |
| Парадигм в группе `COMP,Qual,…` (4 формы) | 7 597 | **4** |
| Парадигм в группе `COMP,…` (4 формы) | 7 136 | **2** |

Обе тег-группы сравнительной степени (`COMP,Qual,…` и `COMP,…`),
дававшие в сумме 14 733 парадигмы (≈82% парадигм shard 0), схлопнулись
до 6 парадигм суммарно — подтверждает механизм «отделить „по" по
Cmp2-разметке до вычисления LCP» именно так, как предсказано в разделе
выше. Итог совпадает по порядку величины с верхней границей,
предсказанной ранее (94.4% байт / 82% парадигм shard 0): реально
получено сокращение таблицы суффиксов shard 0 примерно на 94.5%
(75 618 байт вместо ~1.38 МБ) и сокращение общего числа парадигм с
18 463 (17 934+529, оба шарда) до 3 245 (единственный оставшийся шард)
— около 82.4%. Попутно закрыт и байтовый UTF-8-баг из основного
исследования: доля невалидных как UTF-8 суффиксов в shard 0 упала с
61.7% до 0% — 100% суффиксов валидны как UTF-8.

**Отдельный найденный при этом измерении нюанс, узкий скоуп фикса:** в
реальном `dict.xml` нашлось 3 леммы (`недобитее`, `окологлоточнее`,
`мультипроцессорнее`), у которых базовое слово уже несёт собственную
приставку (недо-/около-/мульти-), и OpenCorpora у них инфиксирует «по»
после этой приставки, а не приставляет её к началу всего слова
(например, `недобитее` → Cmp2-форма `недопобитее`, а не
`понедобитее`). Для этих 3 лемм из ~400K узкий (только `Cmp2`, только
литеральный префикс «по») фикс не подходит буквально — но существующий
fallback-путь `stripCmp2Prefix` (`ok=false`) безопасно обрабатывает их
как раньше (без склейки, но и без порчи данных); это ожидаемое,
осознанное ограничение выбранного узкого скоупа, а не дефект фикса —
см. `TestStripCmp2PrefixRealDictAnomalies` в
`pkg/morphology/importers/opencorpora/real_dict_integration_test.go`.
