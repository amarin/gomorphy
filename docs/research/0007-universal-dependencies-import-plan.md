## Контекст

Пользователь попросил исследовать universaldependencies.org (UD) с точки
зрения формата данных, состава русских словарей/корпусов и возможности
добавить в gomorphy загрузку и импорт русскоязычных данных с этого сайта.
В отличие от этапа 16 (UniMorph), для UD нет черновика этапа — это разведка
с нуля: нужно понять, чем данные UD отличаются от уже поддерживаемых
источников (OpenCorpora, план UniMorph) и стоит ли вообще делать импортёр,
а не просто «формат другой, но то же самое».

Исследование сайта и репозиториев GitHub-организации `UniversalDependencies`
выполнено вживую (см. §«Источники»); ниже — выжимка, релевантная для
принятия решения.

## 1. Формат данных: CoNLL-U

Треебанки UD распространяются в формате **CoNLL-U** — построчный TSV,
10 колонок на слово-токен: `ID FORM LEMMA UPOS XPOS FEATS HEAD DEPREL DEPS
MISC`. Строки группируются в предложения (пустая строка — разделитель),
предложению предшествуют комментарии `# sent_id = ...` и `# text = ...`.

Для морфологии релевантны три поля:
- **LEMMA** — лемма словоформы (как в OpenCorpora/UniMorph);
- **UPOS** — универсальная часть речи, фиксированный список ~17 тегов
  (NOUN, VERB, ADJ, ADP, ...), одинаковый для всех языков UD;
- **FEATS** — список грамматических признаков `Attr=Val`, разделитель `|`,
  например `Case=Nom|Number=Sing|Gender=Masc`; признаки берутся по
  возможности из **универсального межъязыкового инвентаря** UD (это не
  language-specific тегсет, как XPOS, который часто вообще `_`/не
  используется — в русских трибанках XPOS в основном `not available` или
  `automatic`, содержательных данных там нет).

**Ключевое структурное отличие от OpenCorpora/UniMorph:** CoNLL-U — это
разметка **связного текста** (корпус с синтаксическим деревом), а не
лексикон. Строка — это конкретное словоупотребление в конкретном
предложении, не запись «лемма → все формы её парадигмы». Одна и та же
лемма встречается в треебанке ровно в тех формах, которые попали в
исходные тексты — как правило, малая часть полной парадигмы (у
OpenCorpora/UniMorph, наоборот, единица хранения — вся парадигма лексемы).
Это отличие определяет весь дальнейший анализ.

## 2. Состав русских данных на UD

Организация `UniversalDependencies` на GitHub держит 5 репозиториев для
русского (подтверждено выгрузкой списка репозиториев и чтением README
каждого, дата отсечки — релиз 2.18, май 2026):

| Трибанк | Объём | Жанр | Лицензия | Особенности |
|---|---|---|---|---|
| **UD_Russian-SynTagRus** | ~1,4M токенов (крупнейший; 66K+ предложений, ручная разметка + 409K слов добавлены в 2015–2020) | худож. лит-ра, научпоп, новости 1960–2016 | **CC BY-NC-SA 4.0** ⚠️ | Источник — Национальный корпус русского языка; самый качественный (ручная разметка на всех уровнях) |
| **UD_Russian-GSD** | ~16K токенов | Википедия | CC BY-SA 4.0 | Размечен Google; изначально был NC, ограничение снято в 2019 |
| **UD_Russian-Taiga** | ~64K токенов (train+dev+test, v2.9) | блоги, соцсети, отзывы, поэзия, новости, вики | CC BY-SA 4.0 | Авторазметка UDPipe + ручная проверка |
| **UD_Russian-PUD** | 1000 предложений (parallel-корпус) | новости/вики | CC BY-SA 3.0 | Часть мультиязычного parallel-набора, весь трибанк — test-split |
| **UD_Russian-Poetry** | небольшой (не измерялось точно) | русская поэзия XIX–XXI вв. | CC BY-SA 4.0 | На основе Поэтического корпуса НКРЯ + доп. версологическая разметка в MISC |

Суммарно по русскому — 3,455K словоупотреблений (агрегат с главной страницы
UD, совпадает по порядку величины с суммой таблицы выше).

**Лицензионный риск:** крупнейший и самый качественный источник
(SynTagRus) — **CC BY-NC-SA**, то есть несовместим с коммерческим
использованием производного словаря. Остальные четыре — CC BY-SA (более
пермиссивные, но требуют указания авторства и share-alike). Смешивание
источников в одном скомпилированном словаре без учёта происхождения
построчно создало бы словарь, юридически ограниченный самой строгой
лицензией из вошедших источников — тот же принцип уже зафиксирован для
UniMorph в [unimorph.md:274](../unimorph.md).

## 3. Применимость к архитектуре gomorphy

Прямая аналогия с этапами 15/16 (лемма → полная парадигма → DAWG с
payload) работает плохо по трём причинам:

1. **Неполнота парадигм.** Из корпуса извлекаются только наблюдавшиеся
   формы леммы. Для морфологического анализатора это критично — цель
   словаря обычно и есть полнота парадигмы (по любой форме — узнать
   лемму и все остальные формы). Словарь, собранный из UD, для многих
   лемм будет содержать 1–3 формы вместо 10–20.
2. **Разнородность лицензий по источнику** — при слиянии нескольких
   трибанков пришлось бы трекать происхождение на уровне (лемма, форма,
   тег), либо явно отказаться от SynTagRus в пользу компиляции только из
   CC BY-SA источников.
3. **Формат тегов не opaque, а структурирован и универсален** — в отличие
   от UniMorph/тематических словарей, FEATS — это `Attr=Val|Attr=Val`, а
   не одна строка-бандл. Загонять его в существующий TSV-движок (этап 19,
   [todo.md:552](../todo.md)) как непрозрачную граммему-строку технически
   можно (взять весь FEATS как один opaque-тег), но это теряет главную
   ценность UD-данных — структурированность и кросс-язычную
   стандартизацию признаков.

При этом технически формат **пригоден к парсингу и укладке в TSV-подобный
пайплайн**: `LEMMA<TAB>FORM<TAB>UPOS+FEATS` — почти буквально формат этапа
19 (`лемма<TAB>форма[<TAB>теги]`), с той разницей, что теги здесь не
opaque, а имеют семантику, которую было бы жаль выбрасывать.

## 4. Варианты применения (для выбора)

### Вариант A — полноценный источник словаря (по образцу этапов 15/16)

Агрегировать все встретившиеся в треебанке(ах) пары (лемма, форма) →
компилировать в `.dat` через существующий пайплайн (LCP-стем, дедуп
парадигм, шардирование), FEATS сериализовать как opaque-тег `verbatim`
(аналогично UniMorph bundle) или как отсортированный список
`Attr=Val|...`.

- **Плюс:** минимальный инкремент, переиспользует весь опыт этапа 16.
- **Минус:** неполные парадигмы (см. §3.1) — как самостоятельный словарь
  для `Parse()`/`Lookup()` заметно хуже OpenCorpora/UniMorph по покрытию;
  ценность как «дополнительного» словаря (по аналогии с позиционированием
  UniMorph, [unimorph.md:265](../unimorph.md)) тоже под вопросом — он не
  добавляет лексики, которой нет в OpenCorpora, а покрывает её же хуже.
  Licence-риск при выборе SynTagRus.

### Вариант B — эталонный (disambiguated) тестовый корпус

Не компилировать словарь, а использовать CoNLL-U напрямую как набор
проверочных примеров: для каждого предложения — токены с уже снятой
омонимией (FEATS относится к конкретному употреблению в контексте, а не
ко всем чтениям формы). Прогонять `gomorphy Parse()` по FORM и сравнивать
с эталонными LEMMA/UPOS/FEATS — метрика точности анализатора на реальном
тексте, чего сейчас нет (юнит/интеграционные тесты проекта сверяются с
исходными словарями, а не с независимо размеченным текстом).

- **Плюс:** закрывает реальный пробел (снятие омонимии по контексту —
  вне скоупа текущего анализатора, но качество ранжирования чтений можно
  мерить); данные не нужно компилировать в `.dat` — читаются на лету в
  тестах/бенчмарках; лицензия SynTagRus (NC) здесь не проблема — это
  тестовые данные, не часть дистрибутива.
- **Минус:** требует маппинга UPOS+FEATS → внутренний тег gomorphy
  (OpenCorpora-набор) для сравнения — не тривиально 1:1 (см. вариант C).

### Вариант C — источник канонического «универсального» тегсета

Использовать UPOS+FEATS как целевую схему для открытой задачи
«универсальный маппинг тегов между словарями», зафиксированной в
[todo.md](../todo.md) (раздел «Универсальный маппинг тегов между
словарями — НЕ СПРОЕКТИРОВАНО», поднято пользователем 2026-09-16). Один
из нерешённых там вопросов — «Формат «универсального тега» — свой ли
это независимый набор, или сведение к одному из существующих наборов?»
UD FEATS — это уже готовый, документированный, устоявшийся межъязыковой
инвентарь признаков (не изобретённый под gomorphy, а состоявшийся
стандарт с версионированными guidelines), что прямо отвечает на этот
вопрос одним из вариантов.

- **Плюс:** не требует импорта данных вообще — используется только
  словарь признаков/значений (`Case`, `Number`, `Gender`, `Animacy`,
  `Voice`, ... и их значения) как target-схема маппинга; закрывает
  архитектурный вопрос, а не только «ещё один словарь».
  Даёт вариантy B бесплатно как побочный эффект (раз есть маппинг —
  есть и сравнение с эталонным корпусом).
- **Минус:** это дизайн-задача (маппинг OpenCorpora↔UD и
  UniMorph↔UD пары признаков неполны и местами неоднозначны — как и
  отмечено для UniMorph→FT12 в [unimorph.md §5.4]), не инкремент
  импортёра; по объёму крупнее вариантов A/B.

## 5. Рекомендация

Начинать не с варианта A. Полноценный импортёр словаря из UD дал бы
низкую предельную ценность (см. §4.A) при реальном риске лицензионной
путаницы — это отличает UD от UniMorph, где решение «дополнительный
источник» было оправдано (там лексикон, а не корпус). Разумная
последовательность:

1. Сначала — **вариант C** как продолжение уже поднятого пользователем
   вопроса про универсальный маппинг тегов (он всё равно требуется для
   multi-dict, независимо от UD) — но это отдельный дизайн, требует
   brainstorming, как и зафиксировано в todo.md.
2. **Вариант B** — недорогой инкремент поверх варианта C (один и тот же
   маппинг используется и для отчёта конверсии тегов, и для сравнения с
   эталоном); можно сделать и без C, приняв упрощённый частичный маппинг
   только для целей теста.
3. **Вариант A** — не делать, пока не появится конкретный сценарий,
   которому мало OpenCorpora/UniMorph и нужны именно UD-леммы/формы.

## 6. Открытые вопросы (для обсуждения с пользователем)

**Q1.** Согласны ли с приоритетом «C → B, A отложить» из §5, или ценность
варианта A (например, ради жанрового разнообразия — блоги/поэзия,
которого нет в OpenCorpora) недооценена?

**Q2.** Если варианты B/C — в скоуп: маппинг предполагается **ручной
таблицей** (OpenCorpora-граммема ↔ UD Attr=Val) или **программным**
выводом (эвристики по паттернам имён)? Ручная таблица меньше по объёму
(UPOS ~17 значений, FEATS — порядка 30 атрибутов), но требует
лингвистической выверки.

**Q3.** Для варианта B — какой трибанк(и) использовать как эталон? Всё
даёт SynTagRus (крупнее и надёжнее, но NC-лицензия — приемлема для
тестовых данных, не для дистрибутива дальше по цепочке, если тесты когда-
нибудь станут публичным примером/фикстурой с зависимостью на скачивание)
или GSD/Taiga (пермиссивные, но заметно меньше)?

**Q4.** Куда физически кладутся CoNLL-U файлы для тестов — по аналогии с
Q4 из [0006](0006-unimorph-import-plan.md) (ручная загрузка в `.data/ud/`
+ `make test-integration`), или заводить загрузчик?

**Q5.** Нужен ли вообще парсер CoNLL-U как отдельный переиспользуемый
компонент (`pkg/.../importers/conllu` или похожее), даже если варианты
B/C не требуют компиляции `.dat` — то есть нужен только ридер
предложений/токенов, не Builder-пайплайн?

## 7. Оценка объёма работ (черновая, до решения по Q1–Q5)

| # | Задача | Вариант | Оценка |
|---|---|---|---|
| 1 | CoNLL-U ридер (сканер предложений/токенов, без компиляции словаря) | B, C | 0.5 дня |

## 8. Границы применимости

Числа объёма — экспертная оценка по аналогии с этапами 15/16, не
измерение. Не выполнялось: загрузка и парсинг реальных `.conllu` файлов
(только README и формат-спека сайта), оценка качества готовых
маппинг-таблиц UPOS↔OpenCorpora из сторонних проектов (могли уже
существовать в открытом доступе — не проверялось), сравнение с другими
источниками эталонных текстов для варианта B (например, ручная выборка
из НКРЯ вне UD). Решение по вариантам A/B/C и открытые вопросы Q1–Q5 —
не приняты, ждут обсуждения с пользователем.
