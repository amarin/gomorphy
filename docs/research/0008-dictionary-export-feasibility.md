# Оценка реализуемости экспорта словарей в форматы pymorphy2 и OpenCorpora

**Дата:** 2026-09-17
**Статус:** анализ выполнен (чтением кода, без экспериментов), решения по объёму не принимались
**Анализировал(а):** Aleksey Marin (сессия с Claude Code)
**Связанные документы:** [../todo.md](../todo.md) (раздел «Универсальный маппинг тегов между словарями»), [../implementation/stage-15-import-opencorpora.md](../implementation/stage-15-import-opencorpora.md), [../implementation/stage-12-import-pymorphy2.md](../implementation/stage-12-import-pymorphy2.md), [0005-pymorphy2-full-dawg-walk-cost.md](0005-pymorphy2-full-dawg-walk-cost.md)

## Контекст

Задача — оценить, насколько реализуем экспорт внутреннего словаря
gomorphy (`internal.Dictionary`) обратно в исходные форматы: бинарный
формат pymorphy2 (`words.dawg` + `paradigms.array` + `suffixes.json` +
`paradigm-prefixes.json` + `gramtab-opencorpora-int.json`) и XML-формат
OpenCorpora (`dict.xml`). На момент анализа в кодовой базе есть только
импорт в обе стороны (`pkg/morphology/importers/{pymorphy2,opencorpora}`)
— обратного пути (экспорта) не существует ни в каком виде, задача не
упомянута ни в одном файле `docs/implementation/` или `docs/todo.md`.

## Актуальный срез кода (проверено чтением 2026-09-17)

Низкоуровневые примитивы сериализации, нужные для экспорта, **уже
существуют и уже протестированы round-trip'ом** — экспорт не потребует
новой бинарной инфраструктуры:

1. `internal.DAWG.Bytes()` (`pkg/morphology/internal/dawg.go:61`) —
   сериализует DAWG обратно в тот же бинарный wire-формат
   (dictionary+guide), который читает `ReadDAWG`; покрыт
   `TestBuildDAWGRoundtrip`. Формат совпадает с pymorphy2 `words.dawg`
   (`ReadDAWG` уже читает реальные pymorphy2-словари, см.
   [0005-pymorphy2-full-dawg-walk-cost.md](0005-pymorphy2-full-dawg-walk-cost.md)).
2. `internal.Paradigm.Data()` (`pkg/morphology/internal/paradigm.go:57`)
   — обратное преобразование парадигмы в `[]uint16`, симметрично
   `NewParadigmFromData`, который читает pymorphy2 `paradigms.array`
   (`importers/pymorphy2/import.go:167-195`).
3. `Suffixes`/`Prefixes`/`TagSet.Tags` — обычные `[]string`, тривиально
   сериализуются в JSON (формат `suffixes.json`/`paradigm-prefixes.json`/
   `gramtab-opencorpora-int.json` — плоский JSON-массив строк).

Итого: для словаря, у которого `d.Words`/`d.Paradigms`/`d.Suffixes`/
`d.Prefixes` устроены как у pymorphy2 (один шард, без плотного
алфавита), экспорт в pymorphy2-формат — это в основном обвязка уже
готовых кусков, а не новая инженерия.

Три независимых препятствия делают экспорт **произвольного** словаря
(в первую очередь — импортированного из OpenCorpora) в pymorphy2-формат
не тривиальным:

1. **Формат тега различается синтаксисом.** OpenCorpora-импортёр
   собирает тег как граммемы через запятую без пробелов
   (`importers/opencorpora/import.go`, `gramm` в `OnFormEnd`); pymorphy2
   (`gramtab-opencorpora-int.json`) использует пробел перед частью формы:
   `"NOUN,anim,masc sing,nomn"`. Тот же смысл, разный синтаксис — уже
   зафиксировано в `todo.md` («Универсальный маппинг тегов между
   словарями — НЕ СПРОЕКТИРОВАНО») как факт, но без решения.
2. **Шардирование суффиксов не имеет обратного пути.** Механизм
   шардирования (`importers/opencorpora/shard.go`) введён именно из-за
   переполнения `uint16`-лимита числа суффиксов на словарь (см.
   `implementation/code-review-pre-1.0-triage.md`). Слияние нескольких
   шардов обратно в единый `suffixes.json` pymorphy2 рискует воссоздать
   то же переполнение, которое и заставило шардировать.
3. **Плотный алфавит.** Словари, пересобранные `RecompileDense`, сейчас
   даже собственный `SaveTo` отказывается сериализовать (`Alphabet` не
   nil → ошибка, см. раздел «pymorphy2-рекомпилятор под плотный алфавит»
   в `todo.md`). Экспорт в чужой формат для такого словаря либо запрещён
   по той же причине, либо требует предварительной обратной конвертации
   в raw UTF-8 DAWG.

Экспорт в OpenCorpora XML сталкивается с отдельной, более фундаментальной
проблемой — **потерей информации при импорте**, а не только синтаксисом:

4. **Тег формы после импорта — неразделимая склейка.** `OnFormEnd`
   комбинирует граммемы `<l>` (лемма) и граммемы конкретной `<f>` (форма)
   в одну строку тега на форму (см. фикс «Критический баг: искажённые
   теги OpenCorpora-словоформ» в `todo.md`). После импорта восстановить,
   какая часть тега принадлежала лемме, а какая — конкретной форме, без
   эвристик невозможно: это осознанная архитектура импорта (один флэт-тег
   на форму), не побочный эффект бага.
5. **Метаданные схемы не хранятся.** `internal.Dictionary` не несёт
   numeric lemma id, `<links>`, комментарии и ревизии OpenCorpora —
   экспорт в валидный `dict.xml` потребовал бы либо генерации фиктивных
   id, либо признания, что результат — не тот же словарь в другом
   файле, а структурно похожий суррогат.

## Выводы

| Направление | Оценка | Главное препятствие |
|---|---|---|
| pymorphy2-экспорт, словарь **pymorphy2-происхождения** (round-trip) | низкий риск, вся бинарная инфраструктура уже есть | нет |
| pymorphy2-экспорт, словарь **любого происхождения** (в первую очередь OpenCorpora) | блокирован | маппинг тегов (см. ниже) + шардирование + плотный алфавит |
| OpenCorpora XML-экспорт | не рекомендуется как обратимая операция | необратимая склейка тега лемма+форма при импорте; отсутствие метаданных схемы |

Рекомендованный порядок работ, если экспорт будет реализовываться:
1. pymorphy2-экспорт для словарей pymorphy2-происхождения — самостоятельная
   задача, не блокирована ничем из списка выше.
2. Универсальный экспорт (любой словарь → pymorphy2) — блокирован
   отсутствием маппинга тегов; браться до его дизайна не стоит: иначе
   экспорт будет тихо давать некорректные/нераспознаваемые pymorphy2 тегом
   на выходе (тот же класс риска, что дважды уже ловился в проекте —
   `paradigmKeyHash`, накопление граммем в `OnFormEnd`).
3. OpenCorpora XML-экспорт — если понадобится, специфицировать явно как
   «экспорт в XML в стиле OpenCorpora для чтения человеком/сторонними
   инструментами», не как round-trip; п.4–5 выше делают точный round-trip
   нереализуемым без изменения того, что импорт сохраняет.

Прямое следствие: маппинг тегов между словарными форматами — общая
зависимость и для универсального экспорта, и для multi-dict
(`morphology.MultiDictionary`, где `Reading.Tag` сейчас отдаётся как есть,
без нормализации между словарями разных источников) — стоит
проектировать как самостоятельную задачу, не только «под экспорт».
